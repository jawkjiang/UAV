# TIME_PER_POINT修正说明

## 问题发现

用户指出：**实际采样间隔应该是0.167s左右**，而不是配置中的0.01s。

## 数据验证

分析实际数据（test_complete.csv）：

```
Delta_t统计:
  平均值: 0.1543秒
  中位数: 0.1560秒
  第1百分位: 0.09秒
  第99百分位: 0.21秒
```

**结论：实际采样间隔约0.156秒，与用户提到的0.167秒接近。**

## 配置修正

### 修正前
```python
SAMPLING_RATE = 100  # Hz
TIME_PER_POINT = 0.01  # 秒
```

### 修正后
```python
SAMPLING_RATE = 6.4  # Hz (约1/0.156)
TIME_PER_POINT = 0.156  # 秒 (实际数据delta_t的中位数)
```

**错误倍数：15.6倍**

## 影响分析

### 1. 窗口时间计算

| 项目 | 修正前 | 修正后 | 差距 |
|------|--------|--------|------|
| 窗口时间跨度 | 50点×0.01s = 0.5s | 50点×0.156s = 7.8s | 15.6倍 |
| 窗口步长时间 | 5点×0.01s = 0.05s | 5点×0.156s = 0.78s | 15.6倍 |

### 2. MTBFA计算

**修正前（错误）:**
```
总窗口数: 32,405
窗口步长: 0.05秒
总时间: 32,405 × 0.05s ≈ 27分钟
误报: 6次
MTBFA: 27min / 6 ≈ 4.5分钟  ❌
```

**修正后（正确）:**
```
总窗口数: 32,405
窗口步长: 0.78秒
总时间: 32,405 × 0.78s ≈ 7小时
误报: 6次
MTBFA: 7h / 6 ≈ 1.1小时  ✅
```

### 3. 检测延迟（ADD）

| 项目 | 修正前 | 修正后 |
|------|--------|--------|
| ADD | 0.000s（显示为0） | 0.41s（真实值） |

因为修正前时间被压缩了15.6倍，所以0.41秒的延迟显示为约0.026秒≈0。

## 关键变化

1. ✅ **MTBFA从4-5分钟提升到40-80分钟** (约15倍)
   - 这才是真实的误报间隔
   - TCN最佳：1.37小时才误报一次

2. ✅ **ADD从0秒变为0.4秒**
   - 检测延迟约0.4秒是合理的
   - 对应约2-3个窗口的延迟

3. ✅ **DR@1s从100%降至83%**
   - 之前因为时间压缩，0.4秒被算作0秒
   - 现在正确反映：83%的攻击在1秒内检测到

## 用户计算验证

### 用户的理论计算
```
Accuracy = 99%
每100个窗口 → 1个错误
100窗口 × TIME_PER_POINT × STEP_SIZE = 时间
```

### 修正前（错误）
```
100窗口 × 0.01s × 5 = 5秒  ❌
```

### 修正后（正确）
```
100窗口 × 0.156s × 5 = 78秒 = 1.3分钟  ✅
```

### 实际MTBFA
```
测试集约7小时正常时间
6个误报事件
MTBFA = 7h / 6 ≈ 1.1小时 = 70分钟  ✅
```

**符合预期！** 每约70分钟误报一次，这与99%准确率的理论计算（1.3分钟出现1个误报窗口，多个误报窗口合并为事件）基本一致。

## 结论

1. **配置已修正**：TIME_PER_POINT从0.01s改为0.156s
2. **MTBFA现在正确**：约1小时误报一次（而不是4分钟）
3. **检测延迟合理**：0.4秒平均延迟
4. **DR@时间阈值正确**：83%在1秒内检测，100%在5秒内检测

这些指标现在与实际的物理时间一致，可以用于真实系统的性能评估。
